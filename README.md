# ESP32 NTP Stratum 1 Time Server (version 4.0.0-WebUI)

An ESP32 NTP Stratum 1 Time Server for your home network

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

---

## Overview

This is a fork of [Rob Latour's neat ESP32TimeServer Project](https://github.com/roblatour/ESP32TimeServer).

At the moment it features the functions of his release v4.0 plus some changes.
The big one is a Website to change settings and update firmware images.

## What's new in 4.0.0-WebUI

Taken over from Rob's release v4.0 (adapted to this fork, everything set on the website):

- PTP master (IEEE 1588, end-to-end, two-step) over Ethernet, UDP/IPv4 and UDP/IPv6, off by default. It serves only while the server is stratum 1 with GNSS and PPS, and announces itself as a GNSS-locked grandmaster (clockClass 6). Delay_Req rate limit per follower, follower list on the website.
- PTP authentication (AUTHENTICATION TLV, HMAC-SHA256-128, compatible with linuxptp).
- NTP "authentication required": unsigned NTP requests can be refused.
- MQTT / Home Assistant: PTP report and a larger MQTT queue.
- `tools/configTimeSettings.ps1`: sets up Windows Time as NTP or PTP client of the server.
- ESP32-S31 build (experimental, not tested on hardware).

Also new in this fork: RADIUS and TOTP logins of the website (see below).

Not taken over: the change of the internal time scale to TAI (this fork keeps UTC inside and adds TAI - UTC only for PTP).
The fork's version name changed from "WebIf" to "WebUI".

## RADIUS and TOTP logins of the website

The website can check logins against up to two RADIUS servers and ask for a TOTP code as a second factor (taken over from the ESP32-ConsoleServer project). Everything is off by default: the website has the local user `admin` with its password.

**RADIUS servers** (*Security*, *RADIUS servers*): per server a host (an IPv4 or IPv6 address or a DNS name; a name ending in `.local` is looked up with mDNS), the UDP port (1812) and the shared secret (1 to 64 printable characters). Server 2 is asked when server 1 does not answer. Timeout per try 3 s, 2 more tries per server, a server that did not answer is skipped for 2 minutes (*Dead time*, 0 = never skipped). The requests carry User-Name, User-Password (PAP), Message-Authenticator, NAS-Identifier (the host name unless set), NAS-IP-Address or NAS-IPv6-Address (the address the request is sent from unless set), NAS-Port 0, NAS-Port-Id `https`, NAS-Port-Type Virtual, Service-Type Login and Calling-Station-Id (the address of the client); Service-Type and NAS-Port-Type can be changed or left out.

**Who is let in.** An Access-Accept counts from privilege level 15 (*Privilege level at least*, 1 to 15): the level is taken from `Cisco-AVPair` `shell:priv-lvl=N`, without it Service-Type Administrative-User counts as 15 and anything else as 1, as on a Cisco device. *Attribute that must also be in the answer* (optional) asks for one more attribute, compared exactly: `Cisco-AVPair=<value>`, `Class=<value>` or `Filter-Id=<value>`. An Access-Challenge is not supported and refused. *Answers must carry a valid Message-Authenticator* (on by default) drops every answer without a valid one (BlastRADIUS, CVE-2024-3596); the requests always carry one.

**The login methods** (*Security*, *Login to this page*): *Local password* and *RADIUS* can be on together; *Local password only when no RADIUS server answers* decides the order, as `aaa authentication login` on a Cisco device:
- on (default), like `group radius local`: every user name is asked from RADIUS first; only when no server answers, `admin` logs in with the local password. A RADIUS Access-Reject is final.
- off, like `local group radius`: `admin` is checked with the local password only, every other name by RADIUS.
- RADIUS alone: every name, also `admin`, is checked by RADIUS.

With RADIUS on, the login page asks for a user name (empty = `admin`). *Status*, *Login* shows the user and method of your session, the RADIUS servers (last answer, round trip, dead time) and the counters.

**Lock-out guard and throttling.** The local password can only be switched off in a session that RADIUS logged in, so a wrong RADIUS setting cannot lock you out; *Apply* without *Save Settings* is undone by a restart as well. Every refused RADIUS login (also "no answer") counts as a failed login with the same lock-out as a wrong password. At most 2 logins are asked at once and one per source address; a login that waits for RADIUS does not hold up the page. The RADIUS client task and its memory (about 8 kB plus 6 kB stack) are only started once RADIUS is switched on or tested (this board has no PSRAM).

**Test.** *Security*, *Test*: a user name and a password sent to the servers with the values in the form, also before *Apply*. The answer shows the result, the server, the round trip and the attributes. A RADIUS test server of the Python standard library is in the repository:

```
python -I testing/board/radius_server.py --secret testing123
```

**TOTP second factor** (*Security*, *Second factor (TOTP)*): codes of an authenticator app (RFC 6238: SHA-1, 6 digits, 30 s, one step before or after accepted, each code once). *Set up a token* for `admin` or a RADIUS user makes a new key on the device and shows it as a QR code; the first right code of the app stores it and shows 10 recovery codes once (`xxxxx-xxxxx`, each works once instead of a code). *Required for the local user `admin`* (only with a token for `admin`), *Required for RADIUS users*, and *RADIUS users without a token set one up at their first login*. The login page asks for the code after the password (within 2 minutes, three wrong codes and the password is asked again). TOTP needs the time of the device, which comes from GNSS: after a start without a GNSS fix only the recovery codes work. A scripted firmware upload needs the code of `admin` while it is required (`python tools/ote_upload.py --totp ...`) and is refused while the local password is off.

**Stored where.** The RADIUS settings and the check boxes are part of the settings (*Apply*, *Save Settings*); the configuration file (export) carries the RADIUS shared secrets, the website never gets them back. The tokens are stored in NVS at once (up to 9, about 300 bytes each), are not in the configuration file and are erased by *Reset to defaults*. A new token is only stored while NVS keeps room for writing the settings again (*Diagnostics*, *NVS*; a token and one settings set need 237 entries of 32 bytes): with the 256 kB `nvs` of the current partition table all 9 fit. A board that still has the old table (24 kB, see *Partition table and NVS*) has much less room: the test board with an own RSA 2048 certificate stored had 253 free entries.

Third-party code: `THIRD_PARTY_NOTICES` (QR Code generator library of Project Nayuki, MIT).

## Partition table and NVS

`partitions.csv` (since 2026-11-19): `otadata` at `0xF000`, `phy_init`, `factory`, `ota_0` and `ota_1` (4 MB each), `coredump` (128 kB at `0xC20000`) and `nvs` (256 kB at `0xC40000`); `0x9000` to `0xEFFF` is unused, the rest of the flash too. `nvs` holds everything the device stores: the saved settings and the one-shot set of a restart (6996 bytes each), the self-signed web certificate and its key, an own certificate chain and key (up to 8192 and 4096 characters of PEM), the password hash, the allow-list, up to 9 TOTP tokens and a few values of the device (GNSS identity, PPS interrupt and PTP write latency). At the limits that is about 823 entries of 32 bytes, and a changed item is written in full before its old copy is erased. An unchanged settings set (*Save Settings* without a change, the same one-shot set twice) is not written again: ESP-IDF 6.1.1 takes an unchanged blob of more than one chunk (over 400 bytes) as changed and writes it again (`cmpMultiPageBlob()` in `nvs_storage.cpp`), so the firmware compares the stored bytes itself first (`main/custom/nvs_blob.cpp`). The former `nvs` of 24 kB at `0x9000` has 630 usable entries. The firmware finds the partition by its name and runs on both tables.

**Boards updated over the network keep their table.** A firmware upload (web page, `tools/ote_upload.py`) writes only an application slot, never the partition table: such a board keeps the 24 kB `nvs` and its limits until it is flashed over USB with the new table. Measured on the test board with the old table (an own RSA 2048 certificate stored, 253 free entries): up to firmware `2102115` an own certificate chain of 8192 characters was refused with `400` "The certificate could not be stored (NVS: ESP_ERR_NVS_NOT_ENOUGH_SPACE)". A chain of 6000 characters with a key of 4096 was refused the same way, but the new chain was already stored without its key (chain and key were two NVS items, written one after the other): after the next start the stored own certificate was not used ("The private key does not belong to the first certificate of the chain") and the page showed none. In that state *Save Settings* answered `500` "Settings could not be written to NVS", *Restart with updates* `500` "One-shot settings could not be written" and a new TOTP token `507`. Since then chain and key are one NVS item (a power loss or a failed write keeps the old pair or stores the new one) and the room is checked before anything is written: on that board both are refused with `400` "The certificate could not be stored: NVS has 253 free entries, 437 are needed (the certificate and key, and room for writing the settings again)" (508 for the largest pair), NVS stays unchanged and the stored own certificate stays usable. By this check a pair of up to 4286 characters (chain and key together) still fits there; stored and used there: an ECDSA P-256 pair of 2385 characters.

**Own certificate and older firmware.** The own certificate is stored as the NVS item `opair2` (chain and key in one item) with a marker in `okey` (namespace `webtls`). A board keeps its certificate from both earlier layouts: `ocrt`/`okey` of firmware up to `2102115` are used as they are, `opair` of `478c2ff` to `d77f972` is moved into `opair2` at the first start. A firmware from before this change does not read `opair2`: after a downgrade it shows no own certificate (with the own one selected it logs "The own certificate is selected but missing" and serves the self-signed one); a certificate still stored as `ocrt`/`okey` it uses as before. Nothing has to be done for the update back: a certificate stored with the older firmware is the one in use after it, and *Reset to defaults* done with the older firmware leaves no own certificate and no key after it. Not covered, because the items look the same as on a board that never had this firmware: a certificate that `478c2ff` to `d77f972` stored (and no start of this firmware moved since), then *Reset to defaults* with `2102115` or older and afterwards the self-signed certificate selected there; after the update that certificate and its key are stored again (not in use). Erase them with *Reset to defaults* or store another certificate. A firmware from before `ad562e7` (2026-11-04, no own certificate) leaves the stored own certificate in every layout at *Reset to defaults*.

**The new table over USB** (ESP-IDF environment; `COMx` is the port of the board, `build_v3_1` the build folder of its profile). Writing only the partition table keeps the firmware and the boot slot in use; `idf.py flash` writes the new table as well, but also the bootloader and the firmware into `factory`, and resets `otadata` (the device then starts from `factory`). With the new table the device starts with an empty `nvs`: default settings, the password `password`, a new self-signed certificate (new fingerprint), no own certificate, no TOTP tokens. To carry everything over, copy the old `nvs` into the start of the new one (an NVS of 6 pages is a valid NVS at the start of a larger, erased partition; the other pages are then free pages):

```powershell
esptool --chip esp32p4 -p COMx read-flash 0x9000 0x6000 nvs_old.bin   # with the old table; holds the password hash and private keys
esptool --chip esp32p4 -p COMx erase-region 0xC40000 0x40000
esptool --chip esp32p4 -p COMx write-flash 0x8000 build_v3_1\partition_table\partition-table.bin 0xC40000 nvs_old.bin
```

The device then starts with its settings, password, certificates and tokens (the same fingerprints as before). The old region `0x9000` to `0xEFFF` is no longer used but still holds the password hash and the private keys of the web certificates: once the device works with the new table, erase it with `esptool --chip esp32p4 -p COMx erase-region 0x9000 0x6000` and delete `nvs_old.bin`. Tried on an ESP32-P4 (chip v3.2), not on the ESP32-S31.

**ESP-IDF's NVS is corrected by the build.** ESP-IDF 6.1.1 can erase stored items at a start (`components/nvs_flash/src/nvs_page.cpp`, `Page::mLoadEntryTable()`, called by `Page::load()` for each page: the checks of the active page for an item written twice): the check of the last item calls `findItem()` without the chunk index, so when that item is a data chunk of a blob it erases another data chunk of the same blob on that page, and ESP-IDF then erases the blob's index and its other chunks as well: the stored version and the new one are gone. The page is in that state after a reset between the data chunk and the index of a blob update, and after a garbage collection that leaves two chunks of one blob on the active page with a data chunk last. The check in the loop before it erases an earlier item whose 24-bit hash equals that of a later one without comparing namespace, key and chunk index. Measured on the test board with ESP-IDF's own code (firmware `86a128e`, NVS images made from the board's own NVS, one start each): a test blob of 40 bytes with a cut-off update (a version-1 chunk without its index as the last item of the active page) lost both versions; of two number items with the same hash (`zha` and `zcv5bii`) the earlier one was erased; the same blob without the cut-off update and two items with different hashes were kept. Every blob of this firmware can be hit: the saved settings, the one-shot set, the password record, the allow-list, the TOTP tokens and the web certificates. `tools/cmake/nvs_flash_fix.cmake` (from ESP32-WebTherm), included by `CMakeLists.txt` before `project()`, copies ESP-IDF's `components/nvs_flash` (`CMakeLists.txt`, `Kconfig`, `project_include.cmake`, `src`, `include`, `private_include`) into `<build folder>\nvs_flash_fix\nvs_flash` at every CMake configure, replaces the two texts in the copy of `src/nvs_page.cpp` (the chunk index is passed; an earlier item is erased only when namespace index, key and chunk index are equal) and adds the copy to `EXTRA_COMPONENT_DIRS`, where it takes the place of ESP-IDF's component. The copy lies in the build folder, outside the two paths ESP-IDF replaces in `__FILE__` (assert texts); so that its path does not reach the image, the script maps it to ESP-IDF's name of the component (`-fmacro-prefix-map`, added after `project()`): the copy's files read `/IDF/components/nvs_flash/...` like ESP-IDF's own, wherever the build folder is. Every other byte of the copy is ESP-IDF's; only changed files are written (no recompile at an unchanged configure); ESP-IDF itself is not changed; the bootloader builds nothing of `nvs_flash` and is not affected. With the correction, measured on the test board: the cut-off update keeps its old version (after one and after three starts; only the chunk without an index is dropped), both items with the same hash stay, and every item of the board's own NVS is unchanged after a start. The configure step logs `nvs_flash_fix.cmake: nvs_flash is built from ...`. With an ESP-IDF that has both corrections already the script uses ESP-IDF's component and copies nothing; with one in which either text is different (another version) it stops the configure step with a message: then the script has to be looked at for that version. The host test `nvs_hash_test` checks that no two items of the firmware have the same 24-bit hash. Reported upstream as espressif/esp-idf#19212 and #19213 (open on 2026-11-20).

## Lost stored security data

A stored record that is missing at a start reads like one that was never stored, and the firmware would go back to its default for it: the default password, no allow-list, no second factor, the default settings (no required NTP authentication, the default login methods). So the saved settings (`webcfg/saved`), the password record (`webauth/pw`), the allow-list record (`webauth/allow`) and each TOTP token (`totp/t0` to `t8`) have a presence mark (from ESP32-WebTherm, `main/sys/record_mark.cpp`): a number item in the NVS namespace `recmark` (key `<namespace>/<key>` of the record), written after the record is stored and erased before the record is erased; *Reset to defaults* erases all marks before the records (and nothing when the marks cannot be erased). A reset or power loss at any point of a store, a change, the deletion of a token or a *Reset to defaults* therefore leaves a record without its mark (the next start sets it) or with it, never a mark without its record (host test `record_mark_test`, which stops a fake NVS at every write). At every start a valid record without a mark gets one: a board updated from an older firmware gets its marks at the first start with this one. A mark without a valid record means the record was lost (an NVS fault), and then the device does not fall back, until NVS is erased over USB:

- **Saved settings lost**: the defaults are in use, but no time service that a client could take for the owner's: every NTP request (signed or not) is answered as unsynchronised (leap indicator 3, stratum 16, reference `INIT`), so that clients drop this server by themselves; PTP (all transports), MQTT and OTE are off; GNSS and the PPS discipline keep running, the device stays reachable (with the default network settings) and answers ping. Nothing is saved over what is left (the self-signed certificate made for the default FQDN is used but not stored), and no login is accepted at all, as the saved settings may have required a second factor or RADIUS only.
- **Password lost**: no login with the local password, also not with the default one, and no scripted upload (RADIUS logins still work, but neither a password change nor *Reset to defaults* is possible, as both ask for the local password).
- **Allow-list lost**: no source address reaches the web page (every connection is closed).
- **TOTP token lost**: that user (known by a hash of the user name in the mark) is refused after the first factor and cannot get a new token, and the token's slot is not given to another user.

With only the password, the allow-list or a token lost the saved settings are intact and the time service runs as saved (NTP, PTP, MQTT as set). Every such start logs an `E` line naming the record on the console; a refused login is answered `403` "Stored security data of the device was lost: logins are refused. Recovery: erase NVS over the USB port (see the README)", also a scripted firmware upload while the settings or the password are lost, or after the right password while the token of `admin` is lost; `GET /api/info` (no login) has `"security_data_lost": true` (except with a lost allow-list, which lets no connection in), and the login page shows the same text above the password field before any login attempt. The state ends only by erasing NVS over the USB port, which returns the device to its factory state as for a forgotten password (default settings, the password `password`, a new self-signed certificate, no own certificate, no tokens; ESP-IDF environment, `COMx` the port of the board):

```powershell
esptool --chip esp32p4 -p COMx erase-region 0xC40000 0x40000
```

(a board with the former 24 kB table: `erase-region 0x9000 0x6000`), then a reset; or *Reset to defaults* while a login is still possible (a lost token of another user). A firmware from before 2026-11-20 does not know the marks and leaves them when it erases a record. If the device returns to such a firmware after one with marks has started once (also a start that was never confirmed), a *Reset to defaults* or the deletion of a TOTP token done with the older firmware leaves a mark without its record, and the next firmware with marks takes that record as lost (it locks, by design). So do neither with an older firmware; if it happened, the erase of NVS over the USB port is the way back. A change of the password, the allow-list or the settings with an older firmware does no harm. What the marks cannot see: a record lost while it had no mark yet (lost before the first start with marks, or between its store and its mark). A saved set that is there but not usable by this firmware is no loss: as before, the defaults are used and the set is not saved over. The whole NVS is covered by the next paragraph.

**NVS that cannot be used.** When `nvs_flash_init()` fails at a start (`main/sys/nvs_state.cpp`, from ESP32-WebTherm), nothing is erased and nothing stored can be read: `ESP_ERR_NVS_NO_FREE_PAGES` (no free page: the partition is full or was written for another size), `ESP_ERR_NVS_NEW_VERSION_FOUND` (a page of a newer NVS format, written by a newer firmware, e.g. before a downgrade), `ESP_ERR_NOT_FOUND` (the partition table has no `nvs` partition), `ESP_ERR_NO_MEM`, or a read error of the flash. The device then behaves as with lost saved settings: the defaults, every NTP request answered as unsynchronised (leap indicator 3, stratum 16, reference `INIT`), PTP (all transports), MQTT and OTE off, GNSS and the PPS discipline running. The web page comes up with a self-signed certificate made in RAM for that start (a new fingerprint at every start, nothing stored); every login (password, TOTP step, RADIUS) and every firmware upload is answered `403` "Stored data of the device cannot be read (NVS): logins are refused. Recovery: erase NVS over the USB port (see the README)", before any password check and not counted for the lock-out; `GET /api/info` has `"security_data_lost": true` and `"nvs_error"` (the name of the error), and the login page shows that text with the name of the error above the password field before any login attempt. The stored allow-list cannot be read either, so every source address reaches the page; without a session it answers only the page files, `/api/info` and these refusals. Nothing is written to NVS: the measured PPS interrupt latency is not read and not stored (it is measured again about 2 minutes after each such start and used until the next one; the fixed default of 2.5 us applies until then), and the button reset at the start does nothing (a console line says so). The console shows one `E` line at every start, e.g. `E nvs_state: NVS cannot be used (ESP_ERR_NVS_NO_FREE_PAGES: no free page: the partition is full or was written for another size). Nothing is erased; every login is refused and nothing is stored. Recovery: erase NVS over the USB port (every stored setting and key is lost): esptool --chip esp32p4 -p <port> erase-region 0xc40000 0x40000` (offset and size of the `nvs` partition of the table in use: `0x9000 0x6000` on a board with the former 24 kB table); without an `nvs` partition the recovery is the partition table of this firmware, written over USB. The state is decided again at every start: a passing error (no memory) is over at the next start without it, and a partition that was never written (all FF) is no error (a new device starts normally). A new firmware written by an update is kept only when NVS can be used: otherwise the previous firmware is started after the 15 minutes of the check, so a firmware that cannot read what a newer one stored (an NVS of a newer format after a downgrade) goes back to the newer one by itself; a firmware from before 2026-11-22 started on such an NVS runs on the defaults without a web page.

**No memory for reading the stored settings at a start.** Without memory for reading the saved settings the firmware before 2026-11-24 ran on the defaults without a line on it (network, login methods, RADIUS, NTP and PTP keys, MQTT for that start; on the test board the defaults' host name also made it issue and store a new self-signed certificate over the one in use), and a Save would have stored over the saved set; a one-shot set that could not be read for lack of memory was erased without a line. Now the start logs `E web_settings: The saved settings could not be read (out of memory): restart` and restarts (reason `settings_no_memory`; measured with a test build: one restart, then the saved settings), and a one-shot set that cannot be read logs `W ... One-shot settings could not be read (out of memory), ignored` and is erased as before. A restart costs the time service about 20 s without NTP answers. If the memory were missing at every start, the device would restart about once per second without answering NTP (seen with a test build whose forced failure stayed armed); such a restart does not keep a new firmware that is still checked after an update, so after an update the bootloader then starts the previous firmware (not tested with a real loop). The same holds since 2026-11-25 when `nvs_open()` itself has no memory for its handle at the start (ESP-IDF allocates it) for the settings, the web password and allow-list, the TOTP tokens or a presence mark: the firmware before took that for "nothing stored", so a stored set or record (or, for a mark, a record never stored) read as lost for the whole run, with every login refused and a line that says to erase NVS (measured with a test build: `webcfg` failing gave "stored security data lost", the defaults with NTP unsynchronised; the mark of the password failing made the never-stored password read as lost). Now each logs an E line (`... could not be read (out of memory): restart`) and restarts (reason `settings_no_memory` or `nvs_no_memory`; measured: one restart, then the saved settings and the normal logins). `/api/state` answers `503` when that open fails at run time (before: `"saved": null` with unsaved changes).

**No memory for reading the TLS identity at a start.** The self-signed key and certificate of the settings page (NVS namespace `webtls`) are read, parsed and checked at every start. Firmware before 2026-11-26 took a read or a parse that lacked memory for a missing or broken identity: it made and stored a new key and certificate, or issued and stored a new certificate, so the fingerprint changed and every browser had to accept the page again (measured with a test build, each cause made to fail once at a start: the read buffer of the key, of the certificate, the signature buffer of the check that the certificate belongs to the key, and the allocations of mbedTLS in the key parse, the certificate parse, the signature and its check; each start had a new fingerprint and the next start kept it). Now a key or certificate that cannot be read and a key parse that lacks memory give no TLS identity at that start: console `E web_tls: The self-signed key or certificate could not be read (out of memory): none is made at this start` and `E web_admin: Web admin: no TLS identity, the settings page is not available`; the next start uses the stored identity. A check of the stored certificate that lacks memory uses it unchecked (`W ... could not be checked (out of memory): it is used unchecked`). mbedTLS mostly reports a failed allocation inside a parse or a signature as an error of the format or of the key, so the firmware counts the failed allocations of mbedTLS (`mbedtls_mem_failures()`, `main/sys/mbedtls_mem.h`) and takes any during the parse or the check as a lack of memory (also one of another task at that moment: then nothing is made either). Measured with the test build: the same causes, and each of the 92 allocations of mbedTLS in these four steps failing alone at a start: no new fingerprint (FF:2A:BE:70... before and after every case). When `nvs_open()` of `webtls` has no memory, the start has no identity and makes nothing, as before. A start without TLS identity has no settings page, web API or firmware upload until the next start (a reset or a power cycle: there is no page to restart from); the time service does not use the identity and runs: measured in 15 such starts, NTP answered at stratum 1 (5 of 5 requests about 60 s after the restart, each start), and in one with PTP over UDP/IPv4 on, the board sent Sync, Follow_Up (30 each in 30 s) and Announce (15, clock class 6) and answered 29 of 29 Delay_Req. After a firmware update such a start does not keep the new firmware: its check needs the web admin, so after 15 minutes the previous firmware starts (read in `app_update_check_task()`, not measured).

## Replaced and erased data in the flash

ESP-IDF's NVS writes the new value of an item before it erases the old one, and an erase only marks the old item's entries as erased: their bytes stay in the flash until a garbage collection erases that page, which can take a long time. Older firmware left them there, so they could be read from the flash over the USB port: measured on the test board with the firmware of 2026-11-20, the private key of a replaced own certificate (25 of its 26 base64 lines, the last across a chunk boundary), the old password record (salt and hash), a deleted TOTP token (its secret and the hashes of its recovery codes) and a replaced settings set (MQTT password, NTP key, PTP key, RADIUS shared secret), all of these also after *Reset to defaults*; the board's own NVS held 330 such entries of earlier firmware. Now every writer of the firmware opens NVS with ESP-IDF's `NVS_READWRITE_PURGE` (all 20 write opens, `main/sys/nvs_purge.h`, from ESP32-WebTherm): ESP-IDF writes zeros over the old item right after marking it erased. And every start reads the NVS partition once and writes zeros over every entry that is marked erased and still holds data, whatever it belonged to (`nvs_purge_start()`, before anything else writes): the items an older firmware erased, and the rest of an erase that a reset or a power loss cut off (ESP-IDF zeroes an item from its first entry to its last, and its own `nvs_purge_all()` only finds an item whose first entry is still intact). ESP-IDF never reads the bytes of an erased entry (it skips them when it searches, loads a page or copies a page for a garbage collection, and never writes an erased entry again before its page is erased), and writing zeros only clears bits, as its own purge does. The scan follows the page format of ESP-IDF 6.1.1 (pinned by the host test `nvs_purge_test`; `tools/cmake/nvs_flash_fix.cmake` stops the build for an ESP-IDF whose `nvs_page.cpp` has neither the faulty nor the corrected text), and it is refused at build time for an encrypted NVS. Measured on the test board: the first start of this firmware on the board's NVS zeroed 330 entries of earlier firmware on 5 pages in 56 ms (775 entries on 12 pages in 91 ms on an image after many stores), a start with nothing to zero takes 31 ms; the written items stay unchanged; after the same replacements and *Reset to defaults* as above no byte of the old secrets was found and every erased entry was zero. Storing an RSA 4096 own certificate, a settings set or a new password takes up to about 30 ms more. NTP keeps answering at stratum 1 during a store, but an answer that falls into the NVS write of a store can take longer, as before the purge: measured with 40 *Save Settings* in a row and NTP requests 10 times per second, up to 17.7 ms without and 21.2 ms with the purge, 14 of 86 and 33 of 110 of the requests inside a Save at 0.45 ms or more; outside the stores the answers were unchanged (at most 0.37 / 0.33 ms). The T3 of a basic mode answer during a store: see *NTP answers while the web page is used*. Between a cut-off and the next start the rest of the item is still in the flash; a page that cannot be read or written at the start is named by a `W` line `Erased NVS data: ... entries still hold data ...`. Not covered: copies outside the `nvs` partition, namely a core dump in the `coredump` partition (it holds memory of the crashed task, possibly secrets: download it from the page and then delete it), the old 24 kB `nvs` at `0x9000` of a board that was moved to the new partition table and not erased there, and the RAM until the next restart. Without flash encryption the secrets in use (the stored password hash, the keys, the settings with their passwords) can be read over the USB port anyway: the purge only removes what is no longer in use. An older firmware that runs again leaves its replaced items in the flash again; the next start of this firmware zeroes them.

## Secrets in RAM

Every buffer of the firmware that held a password, a shared secret (RADIUS, MQTT), a key (NTP, PTP, TLS), a TOTP secret or recovery code, or a text with such values (a request body and its JSON tree, a settings set, a configuration file, an NVS page read by the purge) is zeroed with `mbedtls_platform_zeroize()` before it is freed or its function returns (`main/sys/secret.h`, from ESP32-WebTherm): the settings sets and the other large objects of the web page when they are deleted (`big_delete()`, `main/sys/big_alloc.h`), every block cJSON frees (the firmware gives cJSON a free function that zeroes first), the stack buffers at every exit of their scope; the key buffers of the NTP and PTP authentication and the MQTT hand-over the same way. An item built for a list or a member of a JSON tree that cannot be added to it for lack of memory (the list or object itself, or an object above it, could not be allocated, or the copy of the member's name) is deleted, so it is freed and zeroed as well (`main/core/json_tree.h`, from ESP32-WebTherm); firmware before 2026-11-25 left such an item allocated with what it held (for example a recovery code of a new TOTP token, or a RADIUS server with its secret) until the next restart: measured on the test board with each allocation of a request failing in turn, internal RAM fell by 22668 bytes over the 1151 failures of `/api/state`, 24096 over 444 of `/api/diag`, 11516 over 149 of `/api/ptp`, 15724 over 124 of `/api/totp/enroll`, 3080 over 314 of the export and 948 over 45 of `GET /api/tls` (78.7 kB in all); now by -40 to +20 bytes for each, the same as without a failure. Firmware before 2026-11-23 did that with a plain `memset()` in many places, which the compiler removed as a store to memory that is not read again (seen in the compiled code: the request body, the PBKDF2 and TOTP buffers, the RADIUS MD5 block, the NVS page of the purge, the NTP and PTP keys and others), and freed every cJSON tree and printed text without zeroing it. Every block mbedTLS frees is zeroed as well (`main/sys/mbedtls_mem.cpp` with `CONFIG_MBEDTLS_CUSTOM_MEM_ALLOC`, installed in `app_main()` before anything there uses mbedTLS (its third statement; blocks that ESP-IDF's `psa_crypto_init()` takes before `app_main()` come from the same heap and are freed through `secret_free()` too); internal RAM as before): mbedTLS zeroes the decrypted data that the HTTP server reads, but ESP-IDF's dynamic TLS buffers free a record buffer whose decrypted data was not read (a request the HTTP server cuts off, e.g. a header longer than 2048 bytes, answered 431) without zeroing it (seen on the board with firmware before 2026-11-24). None of this runs on the NTP or PTP answer path. Not covered: the secrets in use stay in RAM until a restart (the settings in use and the copies the tasks keep of them, the keys of the TLS identity, the password hash, the tables of sessions and TOTP tokens), and the memory of ESP-IDF and esp-mqtt themselves (the header buffer of the HTTP server, the MQTT password copy of esp-mqtt).

## Restarts and the Ethernet MAC

A restart by the firmware (from the website, after an update, after a crash or a watchdog) is a CPU reset, which in ESP-IDF 6.1 leaves the Ethernet MAC receiving: its DMA went on storing frames into the memory of the firmware before until the new firmware created its Ethernet driver, about 0.8 s after the reset, and after an update to a firmware with more variables that memory can hold some of them or the first blocks of its heap (measured on the test board: the DMA was still running at every such start, and after an update to a firmware with 64 kB more variables it wrote a received frame into them in 8 of 8 starts). The firmware therefore stops and resets the MAC before each of its restarts and once more at its start, directly after its variables are cleared (`main/net/emac_halt.cpp`). An update from a firmware without this (before 2026-11-20) relies on the stop at the start alone: a frame that arrives in the 0.7 ms in which the new firmware clears its variables can still land there.

## NTP answers while the web page is used

An NTP answer in interleaved mode (RFC 9769, e.g. chrony with `xleave`) carries the hardware transmit time stamp of the earlier answer as its T3 and is not affected by what follows; PTP is not affected either. An answer in basic mode has to carry its T3 before it is sent: the firmware reads the clock right before the transmit call and adds an estimate of the transmit delay (hardware transmit stamp minus that reading), kept separately for IPv4 and IPv6, with and without authentication.

Measured on the test board (ESP32-P4 v3.1; basic mode requests 8 times per second, or one pair every 2 s where said, the hardware transmit stamp of each answer read back with an interleaved request; error = that stamp minus the T3 in the answer; runs of the fix sessions and of an independent check on 2026-11-24). A client's offset from one answer is wrong by half of its error.

- No web activity during the answers and none shortly before: median 0.02 to 0.08 us, p90 0.2 us, at most 4.0 us (IPv4 and IPv6; signed IPv4 answers at most 4.5 to 7.1 us).
- Inside a web request that makes a TLS handshake (a new HTTPS connection), without any NVS write: the frame left later than its T3 by a median of 5.9 to 19.7 us, p90 17.2 to 41.7 us, at most 32 to 74 us in six runs on one image (firmware of 22be381, before the estimate below). The figures vary that much from run to run on the same image; no upper bound has been established. Inside requests on a kept HTTPS connection: median 0.0 to 7.0 us.
- Inside *Save Settings*: median 18.5 to 29 us, at most 280 to 283 us (the answer itself left up to 16 ms after its request).

**The estimate of the transmit delay** (`main/custom/tx_delay_rule.cpp`, since 2026-11-24; sampling and start changed on 2026-11-25). Up to 2026-11-24 it was the running mean of every sample (weight 1/32): the late frames of a load pulled it up, and the answers after the load carried that larger delay, so they were stamped too late until about 100 answers of the same kind had brought it back (measured: after 60 s of new HTTPS connections back to back the mean went from 13.6 to 47.8 us and the answers of the next 10 s were stamped 26.3 us too late in the median; after 40 s of Saves 13.5 -> 82.6 us and 45.4 us; after one Save 5.3 us, gone after about 5 s). A disturbance only adds delay, so the undisturbed delay is the lower edge of the samples, and without disturbance the samples lie close together (IPv4 -0.4 to +3.9 us around the mean, p90 0.2 us; IPv6 -0.4 to +4.0 us; signed IPv4 -1.2 to +7.1 us, p99 3.8 to 4.2 us; in 6 runs of 1131 answers 11 to 40 per run more than 2 us above, none more than 2 us below). A sample is the hardware stamp (the clock of the Ethernet MAC) minus the clock reading before the transmit call (the clock of the discipline): it is a transmit delay only while the two clocks agree. Now:
  - a sample is taken only while the answer is sent synchronised (stratum 1: GNSS synchronised, PPS disciplined, not in holdover) and not within 60 s after the clock discipline counted a PPS outlier. Before the first synchronisation after a restart the samples ran from -74 to +69 us; one of them (2.7 us) became the start value in a test of the rule of 2026-11-24;
  - the first 16 samples: the estimate is their second smallest, so one low sample among them does not decide it (compensation starts after them, as before);
  - a sample within 2 us of the estimate (either side) moves it by 1/32 of the difference. The band is symmetric so that disturbed samples spread across it do not move the estimate on average (with +5 / -2 us a continuous load without quiet samples walked it up by about 12 us in a simulation on synthetic loads; with +-2 us by about 5 us; on recorded load samples up to 3.5 us over 63 answers);
  - a sample more than 2 us above is not used; only after 1024 of them in a row is the delay taken as lastingly longer, and the estimate becomes the smallest of them. A load gives long runs too: up to 190 answers in a row more than 2 us late at 8 answers per second during 300 s of new HTTPS connections; the count of 2026-11-24 (64) was reached by such loads in a simulation on the recorded samples and after two Save floods on the board, while a lasting growth of the undisturbed delay has no known cause in normal running;
  - a sample more than 2 us below is not used; after 4 of them (only a sample within the band ends that run, a late one does not) the delay is taken as lastingly shorter and the estimate becomes the second smallest of them (on 2026-11-24 the largest, which could itself be a late sample: seen at 17.3 us); a single low sample changes nothing;
  - a new estimate (the start value, a re-based one) is unconfirmed until 16 samples fell within its 2 us band. Until then a sample in the band does not end a run of low ones, and 2 low samples re-base it (to the larger of them). After a restart under a load the start value is a late sample (26 to 39 us above the quiet delay in 10 restarts under load with an image without this step), the late samples near it fall into its band and kept ending the run, so the quiet answers during the load were stamped too late until the load ended. With this step late samples can still confirm a value above the quiet delay before quiet ones come (seen once: about 18 us above for the rest of the load). Two low samples before the confirmation decide the estimate (none more than 2 us below in 6786 quiet samples after synchronisation).
  The band and the run lengths were measured for IPv4 answers without authentication and checked against the quiet spread of IPv6 and of signed IPv4 answers; loads were measured with IPv4 answers without authentication only.

Measured on the board with single requests (every answer spaced from the one before, as a client in basic mode sends them: one request every 0.125 s, or every 0.5 s or 2 s where said; probe `t3p.py --gap`), firmware of `807f1ed` (the rule of 2026-11-24) -> this rule:

The trade: the answers sent during a load are later than their T3 by the whole disturbance, where the pulled mean used to hide part of it. That error has the harmless sign: it adds to the delay a client measures, stays inside the client's bound of half the delay, and a minimum-delay filter (ntpd, chrony) tends to drop those answers. An answer stamped too late has the bad sign: the delay a client measures shrinks and its filter prefers exactly that answer. What bounds that error now is a number of answers of the same kind (IPv4 or IPv6, signed or not), not a time. An answer is stamped before its own sample is taken, so when the estimate is too high the 4 answers whose samples re-base it (2 while it is unconfirmed) carry the old value (more if a sample within the band of the old value comes in between). The estimate is too high after a start under a load with no quiet answer among the first 16 (measured: 0 to 5 answers per run in the first 100 after a restart under load, at most 26.6 us; the start value without the confirmation step: 55 in all, at most 39.1 us) and after a walk within the band (up to 3.5 us, see above). Under such a start the answers that leave without disturbance during the load are stamped too late as well until the estimate is down. With few clients that poll at long intervals, 4 answers can still be minutes. A lasting change of the delay: down after 4 answers; up after 1024 answers of that kind, during which they are early by the change (the harmless sign; with a test build that added 40 us before the transmit call, the count of 64 then gave 4 to 6 s at 16 answers per second).

Seen in these tests, not caused by the estimate: during and after 40 s of Saves back to back (318 to 357 Saves) the clock discipline counted PPS outliers (8 in one run: 4 at 0 to 3 s and 4 more at 31 to 34 s after the end) and its offset reached up to 24 us, more than 5 us for about 50 s, under 1 us again 50 to 80 s after the end; answers in that time were early or late by up to 46 us while the estimate stayed where it was (no sample is taken now for 60 s after an outlier). This is a flood of NVS stores, not normal use: one Save, ten times on two images (0.24 to 0.34 s each), gave no PPS outlier in the 60 s after it and a servo offset of at most 8 to 54 ns; single answers inside the Save left up to 35 us after their T3.

What is known about the cause:

- From the clock reading to the hand-over of the frame to the Ethernet DMA, 7 functions run from the flash, 4214 bytes in all (read from the ELF of 22be381): `process_hardware_ntp_request` (2472 bytes), `get_current_time_in_ntp64_format` (454), `model_ns_at` (306), `write_ntp_timestamp` (60), `transmit_with_hw_timestamp` (454), and FreeRTOS's `xQueueSemaphoreTake` (392) and `pvTaskIncrementMutexHeldCount` (76) for the transmit lock of the Ethernet driver (`CONFIG_FREERTOS_IN_IRAM` is not set). The driver's transmit functions and `memcpy` are in internal RAM, `memset` and the 64-bit divisions in the ROM. Flash is reached through one L2 cache of 128 kB for both cores (`CONFIG_CACHE_L2_CACHE_128KB`); the TLS handshake runs in the web server task on core 0, the NTP task (priority 17) on core 1.
- Cache refills can delay this path: with a test task on core 0 (priority 2, so it cannot preempt anything on core 1) that read 350 kB or 1024 kB of data from the flash, the frames left 47 to 100 us after their T3 in the median (two test builds); with 64 kB, which fits the cache, -1.5 us; with memory copies in internal RAM or a loop in IRAM, no change.
- Not shown: that cache refills are what delays the answers inside a TLS handshake. The NTP task can also be preempted on core 1 by the task of the network stack (lwIP, priority 18, no core affinity) or by interrupts; the measurements show that the delay inside a handshake lies before the transmit call (it took 32 us or more in 7 of 1840 calls), not why. No frame of the web server was waiting on the wire ahead of an NTP answer (by a model of the wire fed with every frame of the network stack), and the network stack was never inside its transmit call when the NTP task made its own.
- A flash write (a store to NVS) stops the other core for its duration (ESP-IDF, `spi_flash_disable_interrupts_caches_and_other_cpu()`), whatever the placement of its code: one answer whose T3 was read just before left 7.7 ms late in one test.

The placement is not changed for this. Placing the 7 functions in internal RAM would be a small change (about 4.2 kB of heap); whether it removes the effect has not been measured, and it would not help during a flash write. For the best accuracy use interleaved mode or PTP, and keep the web page closed during measurements.
